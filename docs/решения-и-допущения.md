# Решения и допущения

Здесь собрано, что я решил сам там, где ТЗ допускало варианты, и что осталось за рамками. Порядок примерно по важности.

## Роли и доступ

- Роль хранится в отдельной таблице профилей, а не в токене и не в метаданных пользователя. Токен можно перевыпустить, а роль в базе читается при каждой проверке, поэтому повысить себе права через клиент нельзя.
- Открытая регистрация отключена. Пользователя создаёт администратор через Admin API Supabase, после этого заводится профиль с именем и ролью. Если у человека нет профиля, войти он не сможет: интерфейс покажет сообщение и выйдет из аккаунта.
- Профиль хранит только имя и роль, почта остаётся в auth. Сотрудники не видят почты друг друга.
- Исполнитель видит объект, если у него там есть хотя бы одна задача. Объект без его задач для него не существует, даже если открыть прямую ссылку.
- Исполнителю в базе разрешено только чтение своих строк. Права на запись в задачи у него нет ни на одну колонку.

## Статусы и история

- Смена статуса идёт одной функцией `change_task_status`. Она сверяет роль, исполнителя и пару «из статуса в статус», а возврат на доработку не пропускает без комментария.
- Прямой `update` поля `status` запрещён триггером для всех, включая постановщика. Так остаётся ровно один путь смены статуса, и его нельзя обойти запросом извне.
- История пишется триггером на сервере, автор записи берётся из текущей сессии, поэтому подделать «кто перевёл» нельзя. На таблицу истории нет прав на запись у клиента, а триггер запрещает правку и удаление даже владельцу через API.
- Комментарий хранится в записи истории, а не в карточке задачи: комментариев к переходу может быть несколько, и каждый привязан к своему переходу.
- Изменение текста задачи, исполнителя или объекта в историю не пишется. ТЗ говорит об истории смены статусов, поэтому я не расширял её до полного аудита полей.
- Новая задача всегда создаётся в статусе «Новая». Сразу в «В работе» её назначить нельзя: сначала исполнитель должен сам её взять.

## Объекты и задачи

- Удаление объекта удаляет его задачи и историю по каскаду. Задачу и объект удаляет только постановщик.
- Правка объекта доступна только постановщику: ни адрес, ни название исполнитель не меняет.
- Исполнителя задачи можно переназначить в любом статусе, кроме принятой: ТЗ не запрещает, а на практике задачи перекидывают. Если это лишнее, ограничение добавляется одной проверкой в триггер.
- Отдельного экрана «все задачи» у постановщика нет: задачи сгруппированы по статусам в карточке объекта, а общий список доступен на странице объектов. Для объёма «2–3 объекта» этого хватает, но при десятках объектов понадобится страница со сводкой.

## Интерфейс

- Действия в карточке задачи показываются только те, что доступны роли в текущем статусе. Это удобство, а не защита: реальные проверки всё равно в базе.
- Ошибки базы показываются как есть, тексты отказов написаны по-русски и объясняют причину («переход запрещён», «возврат требует комментария»).
- Регистрацию и управление сотрудниками через интерфейс не делал: по ТЗ пользователи создаются вручную в Supabase.

## Что не успел и сознательно не делал

- Нет пагинации и поиска по объектам и задачам. На семи задачах это не нужно, на реальном объёме понадобится.
- Нет обновления в реальном времени: после действия данные перезапрашиваются, но чужое изменение подтянется только при обновлении страницы. Supabase Realtime сюда встаёт без переделки схемы.
- Нет вложений, сроков и приоритетов у задач, нет уведомлений на почту.
- Нет автотестов на фронтенд. Проверка безопасности вынесена в отдельный скрипт `scripts/check-security.mjs`, который гоняет запросы от имени ролей и печатает результат; это одна команда, но не CI.
- Демо-данные созданы скриптом, а не руками: так их можно пересоздать на чистой базе (`node scripts/seed.mjs`).

## Ограничения стенда

- Проект на бесплатном тарифе Supabase: после недели без запросов база уходит в паузу и просыпается по первому обращению.
- Пароли демо-учёток одинаковые и простые намеренно, чтобы проверка занимала минуту. Для рабочего контура их нужно заменить.
- Секретный ключ Supabase лежит только в локальном `.env.local` и используется скриптами миграций и засева. В репозиторий он не попадает, в клиент уходит только publishable-ключ.
